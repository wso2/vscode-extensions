# Platform dependencies of the VS Code extensions

The WSO2 Integrator and Ballerina extensions reach WSO2 Cloud through
`@wso2/wso2-cloud-client` and the `ipaas-service` API. The client only wraps
what the API offers; everything the old Choreo CLI did that the platform has
no counterpart for is listed here as a dependency on another team, with the
extension behaviour until it lands. Each item is meant to become one ticket.

| # | Needed | Owner | What the extensions do until then |
| --- | --- | --- | --- |
| D-1 | A public PKCE client for the editors on ThunderID in dev, stage and prod; the full sheet is [thunderid-client.md](thunderid-client.md). Client id `WSO2_INTEGRATOR_EXTENSION`, registered on dev 2026-11-06; stage and prod still to do. Redirect URIs: `vscode://wso2.wso2-integrator/signin`, `vscode-insiders://wso2.wso2-integrator/signin`, `wso2-integrator://wso2.wso2-integrator/signin` (the desktop app), `http://127.0.0.1:10441/callback` through `:10444`. Refresh tokens on, a `revocation_endpoint` in discovery, and `prompt=login` (or the equivalent) showing the organization picker again. | Identity | Sign-in fails with `invalid_client`; the id is overridable with the hidden setting `integrator.advanced.cloudClientId` for testing. |
| D-2 | The platform's services accept the `WSO2_INTEGRATOR_EXTENSION` client and its token audience (`urn:wso2:cloud:platform-api` on dev) the way they accept the `WSO2_CLI` client: the API, the git integration behind `/git/{proxyPath}` (which the API consults with the caller's token before every build), and billing. Done on dev 2026-11-07; stage and prod still to do. A token exchanged for the API URL (`tokenExchange: "resource"` in `environments.ts`) is no alternative: ThunderID does not grant this client the exchange grant. `CHECK_INTEGRATION=<project>/<integration> pnpm check-access` probes the git integration with the token a build uses. | WSO2 Cloud | Without it, sign-in works but API calls answer 401; with the API done and the git integration not, no build can start ("git integration unavailable"). |
| D-3 | Confirmed console and observability-proxy base URLs for stage and prod. The development console host is set through `WSO2_CLOUD_CONSOLE_URL` and its integration route is `/integration/organizations/{org}/projects/{project}/components/{integration}/overview` (confirmed 2026-11-06); whether stage and prod follow the same host pattern, and the organization and project pages' default views, are still to confirm. | Docs / WSO2 Cloud | Open-in-console links follow the dev route (`buildConsoleUrl`); build and runtime logs use the dev proxy pattern. |
| D-4 | The cloud editor injects a ThunderID access token through `WSO2_CLOUD_TOKEN_FILE` (preferred, re-read on every call so it can rotate) or `WSO2_CLOUD_TOKEN`. `CLOUD_STS_TOKEN` is read as a legacy name for one release. | Code-server image | The legacy variable still works; a Choreo STS token in it is rejected by the API. |
| D-5 | git-app-service routes behind `/git/{proxyPath}` documented: list installations, check repository access, the connect-GitHub URL, branch listing for private and non-GitHub repositories, and a push credential for the editor. | WSO2 Cloud | Public GitHub only: branches come from `/repos/{owner}/{repo}/branches`; "Connect GitHub" opens the console; the deploy form accepts any URL but the platform refuses private sources with `sourceBindingError`; the editor asks for git credentials. |
| D-6 | The Copilot `token-exchange` endpoint and the managed-token-service accept a ThunderID access token as the subject, and the managed-token-service gets a base URL per environment. **Checked on dev 2026-11-06:** the Copilot exchange answers 400 to a `WSO2_INTEGRATOR_EXTENSION` token (`scripts/check-access.js` with `WSO2_COPILOT_URL`), so Copilot does not yet accept the ThunderID subject. | AI backends | Copilot single sign-on from the WSO2 Cloud session fails over to the other login methods; managed (OAuth) connections report "not available on WSO2 Cloud yet" unless `WSO2_CLOUD_MANAGED_TOKENS_URL` is set. |
| D-7 | Connection objects on the platform: a catalog of exposed endpoints across the organization, connections with generated env-var names, an audited way to read a secret back, and a local network bridge for project- and organization-internal services. | WSO2 Cloud | Connections are env-var groups: database connections write the server's credentials as a sensitive group; service connections write an endpoint URL and an API key. Secret values never read back, so a local run warns which variables to set by hand; third-party service registration is refused with a message; organization/project-only services are unreachable from a laptop. |
| D-8 | Pagination on `/projects`, `/projects/{p}/components` and `/components/{c}/builds`; the repository in the component list; the build-trigger response naming the run. | WSO2 Cloud | Lists are capped at what the API returns; the repository is fetched per component and cached; a triggered build is found by diffing the list. |
| D-9 | Component types for workflows and libraries; confirmation that `PUT /components/{c}/build-parameters` followed by a build converts a prebuilt or API-born MCP server into a source one; per-environment database users. | WSO2 Cloud | Workflow and library integrations cannot be deployed from the editor; prebuilt and MCP attach use the build-parameters route and are flagged as unverified; database connections use the admin user. |
| D-10 | The API's own build-log route fixed, or `/observability/{proxyPath}` sanctioned. | WSO2 Cloud | Logs go to the observability proxy directly; the client switches with one line. |
| D-11 | Auto deploy for Ballerina integrations. `PATCH /components/{c}/auto-deploy` answers "auto-deploy is turned off for Ballerina integrations: deploy builds from the Deploy page" on dev (2026-11-06), and `autoDeploy: true` in the create body does not change that. The old Choreo CLI switched auto build and auto deploy on for every integration it created. | WSO2 Cloud | WSO2 Integrator follows the first build itself and deploys it to the pipeline's entry environment (`followFirstBuild` in `create-component-cmd.ts`); later pushes build automatically but are not deployed. |
| D-12 | The gateway in front of ipaas-service gives up on `POST /components/{c}/deployments` before the platform answers (504 "upstream request timeout", dev 2026-11-07, first deployment of a new Ballerina integration) while the deployment goes ahead: the release appeared and rolled out in the console. The client reads the environment for up to 90 seconds after such an answer and takes the deployment it finds as the accepted one (`DeployResult.observed`); the release name from the lost answer is unknown then, so the rollout wait follows whichever release is current. A longer gateway timeout on that route, or an asynchronous accept (202 with the release name) would make this unnecessary. | WSO2 Cloud | Without the follow-up read, every first deploy from the editor reports an error that is not one. |

Two defects found in the published OpenAPI document while generating the
types are patched in the client's copy of the spec and recorded in
[`../spec/README.md`](../spec/README.md): undeclared `traceId`,
`traceStartTime` and `traceEndTime` parameters, and an example under
`PolicyRules.operations` that is not valid for its schema.

## Environments

Production and staging hosts are in `src/config/environments.ts`. The
development deployment is internal; its hosts are not in this repository and
are supplied through `WSO2_CLOUD_API_URL`, `WSO2_CLOUD_ISSUER`,
`WSO2_CLOUD_OBSERVABILITY_URL` and `WSO2_CLOUD_CONSOLE_URL`, or the hidden
`integrator.advanced.cloud*` settings, with `CLOUD_ENV=dev`.
